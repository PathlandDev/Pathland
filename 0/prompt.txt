I got the follwing suggestion. Tell me what you think. Feature: safe, ergonomic external UI updates (actor-thread signal handoff)
Context
Pathland 0.2.1, as used by Quarkus 3.39+ and Spring Boot hosts. Views are authored in the Kotlin DSL with WritableSignal, computed, and effect. Pathland signals are documented as single-threaded by contract, and PathlandRegistry serializes all session work on a single actor thread.
Problem
External event sources — Kafka/SmallRye @Incoming consumers, scheduled jobs, DB notifications, websocket clients, etc. — run on non-Pathland threads. There is no supported way to update a live session’s signal from such a thread.
A signal injected into the Pathland environment can physically be set from a consumer thread, but that runs the emitter/binding effects and delta generation on the consumer thread while the session actor may be rendering the same tree. That is a data race. The current public alternatives are all unsatisfactory:
- an explicit UI Refresh button (requires a user click),
- resync(...), which only re-emits the retained tree and does not re-run body(),
- reflection into private registry/session state,
- client-side script hacks.
This is a common server-driven-UI requirement and should be a first-class Pathland feature.
Goal
Add a thread-safe, non-blocking API for external code to update live Pathland UIs while preserving the actor model and producing normal fine-grained deltas.
Proposed design
1. Core actor primitive
Add an explicit actor handoff to the server core:
public interface PathlandSession {
    /** Safe from any thread; runs on this session's actor. */
    void submit(Runnable task);
}

public final class PathlandRegistry {
    Set<String> sessionIds();
    void submitAll(Consumer<PathlandSession> action);
    AutoCloseable onSession(Consumer<PathlandSession> onOpen,
                            Consumer<PathlandSession> onClose);
}
Requirements: work is serialized on the existing actor, dropped after shutdown, and exceptions are logged without killing the session.
2. App-level signal hub
Provide an app-scoped hub with a canonical value and per-session mirrors:
public interface PathlandSignalHub {
    /** Safe from any thread; non-blocking, coalescing. */
    <T> void publish(String name, T value);

    <T> WritableSignal<T> appSignal(String name, T initial);
}
- publish never touches a session’s reactive graph directly.
- It schedules, per subscribed session, an update of that session’s local WritableSignal on the session actor.
- The local signal triggers the existing effect/delta path.
- Latest-wins per (session, signal); bounded queues; metrics for published/coalesced/dropped.
- Subscribe on session open, unsubscribe on close; no work after close.
3. Environment integration
Bind a session-scoped SessionSignals object at the root, similar to Platform.ACTIVE_PATH:
EnvironmentKey<SessionSignals> SESSION_SIGNALS =
        EnvironmentKey.of("pathland.sessionSignals");

public interface SessionSignals {
    <T> Signal<T> signal(String name, T initial);
    void submit(Runnable task);
}
View usage:
val count = Environment.value(SESSION_SIGNALS)
    .signal("customer-events.count", 0)

Text(computed { "Customer events consumed: ${count.get()}" })
External producer:
@Incoming("customer-channel")
void onCustomer(CustomerCreatedEvent event) {
    hub.publish("customer-events.count", counter.incrementAndGet());
}
The host should bind SessionSignals automatically; app authors should not need per-session plumbing.
4. Multi-node
Design publish to be node-agnostic. A follow-up can back it with Redis pub/sub or a versioned state store, with each node fanning out to its local sessions. Ignore stale/duplicate updates. Pathland already has pathland-state-redis to build on.
Non-goals / constraints
- Do not make WritableSignal.set asynchronous or magically thread-safe; keep its synchronous semantics.
- Do not share one global WritableSignal across sessions without per-effect actor dispatch; that creates cross-session races.
- No breaking changes to existing public APIs; prefer additive APIs.
- Keep both Quarkus and Spring Boot hosts working; the core must stay framework-agnostic.
- No unbounded queues or blocking producers.
Acceptance criteria
- A Kafka/SmallRye consumer can call hub.publish("counter", n) from its worker thread, and a live view’s computed text updates via a small delta — no Refresh button, no resync.
- All signal reads, writes, and effect execution occur on the session actor thread; add an assertion/test for this.
- Multiple sessions receive independent updates; closing a session cancels pending updates.
- Rapid updates coalesce to the latest value without unbounded memory growth.
- Works in both Quarkus and Spring Boot test harnesses; include a Quarkus test with a background thread and a multi-session test.
- Docs: API documentation plus a short “external updates” guide using the Kafka example; update any relevant spec/architecture notes.
