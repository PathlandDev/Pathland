You are migrating Java files in the Pathland repo to the v2 authoring surface. This is a precise, mechanical rewrite — you may ONLY edit files under `lib/java/pathland-demo-views/src/main/java`. Do NOT edit anything else.

Goal: rewrite every view construction from the legacy `.of(...)` + `.with(...)` style to the v2 `with(Consumer)` builder + `.modifiers(...)`/`.children(...)` fluent surface (spec `spec/DSL.md` §2, §4, §5). The library (`lib/java/pathland-view`) ALREADY defines the v2 entry points.

## The v2 surface (read the actual class files to confirm signatures)
Each concrete view exposes static entry points returning a `ViewBuilder`:
- `Text.with(t -> t.text("hello"))`  — value config
- `VStack.with(v -> v.alignment(HorizontalAlignment.LEADING).spacing(8)).children(a, b, c)` — configure + children
- `.modifiers(mod1, mod2, ...)` — apply modifier values (innermost-first), chainable in ANY order with `with(...)` and `children(...)`.

Every modifier class has a `with(Consumer<Config>)` static factory; single-value enum/Font/Style types are themselves the modifier.
`FontWeight.BOLD`, `Font.system(18f)`, `Font.headline()`, `TextAlignment.CENTER`, `Truncation.TAIL`, `TextCase.UPPERCASE`, `ControlSize.REGULAR`, `FontDesign.ROUNDED`, `FontStyle.ITALIC`, `PlainButtonStyle.INSTANCE` and other `ButtonStyle`/`LabelStyle`/`AudioStyle`/`VideoStyle` instances are modifier VALUES you pass directly to `.modifiers(...)` — never a `*Mod.of(...)` wrapper.

## Rules
1. Preserve the `View`/`ViewBuilder` types: after the whole fluent chain the result is a `View` — assignable to any `View`, `View a`, or return type. If a local variable was typed `VStack`/`Button`/etc. and now holds a `ViewBuilder`, change the variable type to `View`.
2. `.modifiers(...)` chains: `Text.of("x").with(A, B)` becomes `Text.with(t -> t.text("x")).modifiers(A, B)`. Note `.with(A, B)` on a concrete view instance (the old View instance method) becomes `.modifiers(A, B)` on the builder.
3. When a karaoke/`computed`/`Signals.computed(...)` or `Environment.value(...)` or `Signal` is passed to a value config, keep it — the config setters accept `Signal<T>` overloads.
4. `Color.rgb(...)`, `Color.argb(...)`, `Color.token(...)`, `Color.WHITE`, `Color.CLEAR`, `Color.BLACK` are unchanged.
5. `Commands.Size.FILL` and `Commands.Size.HUG` in `Frame` configs: use `.width(Commands.Size.FILL)` / `.height(Commands.Size.FILL)`.
6. Do NOT reformat code beyond your edits (no unrelated whitespace changes).
7. If you find a construct you cannot map with certainty, consult the corresponding class file under `lib/java/pathland-view/src/main/java/com/pathland/view/` to confirm the `Config` setter / `with` signature, then translate correctly. Never guess — read.
